## Unreleased (0.5.0)

- 0.5 (breaking, rules 20 / 21 and escalation): `Authorize` evaluates `envelope.units`, `envelope.tighten` and `model_polarity` as the TypeScript verifier does (`units` and `tighten` checks, exact reasons, the host `env`, `IntentV2Context` accepts `policy.model_polarity` and `env`; `AuthorizeResult.Degraded["tighten"]` for a `legacy` pass). `Verdict.Reasons` keeps every failing intent-v2 check's reason (`FoldV2Reasons`), so a multi-check escalation stays an escalation. `VerifyEscalationAnswer` takes `[]PinnedSigner` and accepts every suite this build implements under the TypeScript pin rules (`EscalationPinned` pins a PQ key). `StateStore` used with escalation principals must implement `LastStore` (`SQLStateStore` now does): `Authorize` refuses it as `authorize_config`, `RequirePCA` panics at construction. `DecideTighten` / `DecideUnits` reasons, null `tighten`, UTF-16 lengths and anchors match the reference; `MeetAll`, `ModelPathsRead`, `EscalationRequestTTLMs`. Several simultaneous violations in one object are reported in the reference's key order (Go records the text order of parsed objects; Rust enables serde_json `preserve_order`, so `serde_json::Map` keeps insertion order); a truncated escalation reason keeps a lone high surrogate exactly as the reference does and is written as `\\udXXXX` (`EscalationReasonsWire`, `escalation_reasons_wire`). `pepDecision` returns anything but an answered escalate unchanged (a string that is no decision included), and integer-valued numbers spelled `2.0` or `1e3` are read as the integers they are (escalation answers, unit exponents), as in the reference. Shared vectors: `decision-vectors.json` (regenerated), `model-rules-vectors.json`.
- **Breaking:** `RequirePCA` defaults to the full `Authorize` path. Without `Authorize` options every request is refused with 403 `authorize_config` naming the missing components; it never falls back to signature-only. The signature-only guard is the explicit opt-in `RequirePCAOptions{SignatureOnly: true}`. Setting both `SignatureOnly` and `Authorize` panics at construction.
- **Breaking:** the core verifier's `counter` check is now `counter_format` (in `Verdict.Checks` and in its reason, `counter_format: missing or not a non-negative safe integer`). `counter` is no longer emitted.
- **Breaking:** `Authorize` reports the stateful replay check as `replay` (reasons `replay: N is not greater than last seen M (replay)`, `replay: N was already claimed (replay)`, `replay: the replay store failed (fail closed)`). `DefaultRequiredChecks()` is now `counter_format, replay, revocation, plan_root_authorized, audience, validity, grant_ref_bound, operation, params_digest, policy`. The name `counter` in `AuthorizeInput.Require` stays accepted as an alias of `replay`.
- **Breaking:** an envelope predicate denial names the unmet limit when a predicate is in scope: `amount <= 100 not satisfied for payments.send on payments/acme`. When no predicate is in scope the reason is still `no predicate permits <verb> on <resource>`.

- 0.5 (additive, extension layer): ledger and optimistic-path verifiers over parsed JSON, checked against the shared `optimistic-vectors.json` and `ledger-vectors.json` (541 vectors, zero disagreement with the TypeScript reference). Ledger: `VerifyLedgerConsistency` (RFC 9162, uint64 index arithmetic, safe-integer sizes), `VerifyLedgerInclusion`, `VerifyTreeHead`, `VerifyWitnessCosignature(s)` (k-of-n), `VerifyHeadConsistency` (signed `prev_root` link for adjacent heads), `VerifyCheckpointChain`, `VerifyWitnessedHead`, `DetectEquivocation`. - 0.5 (additive): the session-history functions of Intent Layer v2 (`inWindow`, `accKeyOf`, `accPreState`, `accPost`, `monitorStep`, `monitorState`, intent_history.go) mirror the TS reference, and the conformance file `intent-state-vectors.json` (3,045 cases: accumulators, monitors, histories, sequencer receipts and key sets) runs through the same adapters as the k042 oracle with zero disagreement.

## 0.4.1

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. In Go: `PolicyCaveats(grant, chain any) any` and `EvaluateCaveats(caveats any, ctx map[string]any) (ok bool, failed []string)` (caveats.go), total and fail-closed; `ctx` uses the conformance field names (`now`, `delegation_depth`, `blast_radius`, `reversibility_class`, `recent_action_times`, `action.params`). Implemented: `max_spend`, `expires`, `not_before`, `rate`, `max_blast_radius`, `reversibility_max`, `delegation_depth`, `budget_alloc`; every other type (note, a second envelope, predicates, tool_schema, unknown) is unsatisfied. `VerifyPCActnCore*` and the `RequirePCA` middleware are unchanged: they do not evaluate caveats; a resource server enforcing a grant's caveats calls `EvaluateCaveats(PolicyCaveats(grant, chain), ctx)` with its own action params. Runs the new `primitives.caveat_eval` corpus section.
- Wire: threshold share signatures are validated PER SUITE (they were a fixed 64 bytes, so a pure ML-DSA-65 share could never be carried). `alg` absent == ed25519 (64-byte `sig`, no `pq_sig`); `ml-dsa-65`: 3309-byte `sig`, no `pq_sig`; `hybrid-ed25519-ml-dsa-65`: 64-byte `sig` + 3309-byte `pq_sig`; a non-string `alg` (incl. null) or an unknown suite fails wire. A share's `pq_pk` is not judged by wire (the threshold check judges it). The wire reason is now `threshold.shares[i]: 'sig' is not canonical base64url (N bytes) for alg '<alg>'`. The conformance runner skips `requires:"<alg>"` vectors for suites Go does not implement (ml-dsa-87, slh-dsa-sha2-128f).
- BREAKING (security): the `PCA-Action` header is STRICT unpadded base64url of UTF-8 text. New exported `DecodePCAHeader(value string) (string, error)` (`ErrPCAHeader`): non-empty, alphabet `A-Z a-z 0-9 - _` only, no `=`, no whitespace (nothing trimmed), length mod 4 != 1, zero trailing bits, then strict UTF-8 (a leading BOM is kept). The middleware's lenient decoder (padded fallback) is removed; any failure takes the existing 401 "PCA-Action header is not valid base64url" path. Runs the new `primitives.pca_header` corpus section.
- Version: Go module versions are git tags (no version string in the sources); release this as `v0.4.1`.

## Unreleased (BREAKING)

- Depth (robustness): `ParseJSONLenient` (the fixture loader) now has a safety depth cap (`MaxLenientDepth` = 131072): hostile depth is an error instead of a fatal goroutine stack overflow, which `recover()` cannot catch. The strict profile, `Canonicalize` and every protocol digest were already capped at `MaxJSONDepth` (32) like the reference; new boundary tests at 31/32/33/100000 for parse, canonicalize and the verify entry points.
- R6-03/R6-04 (parity): new exported `VerifyThresholdShare(entry any) bool` and `SignerSetHash` (promoted from the test helper) validate the WHOLE signer set like the reference: unknown or wrong-case roles, malformed keys, empty / null / short `pq_pk` anywhere, one key per role, one role per key, a duplicate (role, key) only with the same `pq_pk`; `t` must be 1, 2 or 3 (0..255 was accepted); `share.role` is required. The signer-set hash now carries `pq_pk:""` like the reference (it was dropped).
- R6-05 (robustness): `VerifyChain` / `VerifyChainPolicy` recover from any panic into a refusal, and the per-hop type check now also requires `alg` / `pq_pk` / `pq_sig` to be absent or strings (a hop with a numeric `pq_pk` was accepted). `VerifyThresholdShare` is total for any JSON value.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.
- (Go has no public share API; the conformance helper in `conformance_test.go` mirrors the pinned semantics.)

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `VerifyChainPolicy` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Signature: `VerifyChainPolicy(chain []any, expectedRootIssuer string, haveIssuer bool, allowed []string, pqPins map[string]string, trustedRoot map[string]any) (string, bool)`. A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `trustedRoot` is the root itself (same content hash, i.e. the verifier's stored grant), or `pqPins[root.issuer]` equals the root's `pq_pk` (a differing pin is a refusal). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Migration: callers of `VerifyChainPolicy` add `nil, nil` for the old behaviour on Ed25519 roots, and pass `pqPins` (or `trustedRoot`) for any root they did not load from their own store; `VerifyChain` keeps its signature and now refuses every non-ed25519 root. `VerifyPCActnCore` is unchanged in behaviour (it passes its grant as `trustedRoot`). Internally one `resolvePqVerifyKey` choke point mints the only key type (`pqVerifyKey`) that `verifyLeafSuite` / `mlDsa65VerifyB64u` accept, so PQ verification cannot be called with the artifact's `pq_pk`; threshold shares and `pq_artifact` primitives use the explicitly named `callerVouchedPqKey`.
