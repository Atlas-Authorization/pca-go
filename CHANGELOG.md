# Changelog

## Unreleased (0.5.0)

- **New (DX):** `Protect(ProtectOptions)` returns `RequirePCA` options (plus `Middleware()` and `Revoke(grantID)`) with secure defaults: grants from a list or function, an in-memory replay store, a revocation source, the single-step plan; caller-supplied `Authorize` fields win. No catalog risk (Go has no connector catalog). `ExplainRefusal(reason)` returns check / meaning / fix / docs (same table as the TypeScript `explainRefusal`). `RequirePCA` refusal bodies gain a `doc` member (reasons unchanged). Example: `examples/gin-server` (separate module).
- **New (native signing, agent side):** `agent.go`, the producer half of the module, so an agent never needs a TypeScript process: `NewKeyPair` / `KeyPairFromSeed`, `MintGrant` (envelope, salted goal commitment, `holder_pq`), `Delegate` / `Attenuate` (append-only caveats; `SealedCaveat`, `MaxUsesCaveat`, `NeedsDischargeCaveat`), `CommitPlan` with Merkle proofs, `BuildPCActn` (signed `aud`/`iat`/`exp`/`nonce`, optional signed slots), `PCAHeaders`, `SignEscalationAnswer`, `SignDischarge`, `SignNarrow`, `IssuePassport` / `SignPassport`, `SignWorkflow` / `SignStepReceipt`, `SignReadGrant`, `SignAggregateGrant`, `SignFreshAt` and the `Agent` client (`Act`, `Delegate`, `UsePlan`: counter, nonce and header handling). Post-quantum signing through circl: ML-DSA-65, ML-DSA-87, SLH-DSA-SHA2-128f / 256s, their hybrid suites and the nested hybrid (`GeneratePqKeyPair`, `SuiteOpts`); fn-dsa-* and less-cat1 are verify-only (`ErrUnsupportedSigner`; circl has no FN-DSA and no vetted Go implementation exists). Deterministic outputs reproduce `producer-vectors.json` byte for byte (`agent_test.go`, which also round-trips every artifact through this module's verifier).

- **Breaking (security default, K5):** `plan_root_authorized` is now enforced by default. When no plan nodes or plan authorization are configured (no `Context.Plan`, no `Plans` registry, `Plan` not `single-step`), `Authorize` fails the check with `plan_root_authorized: default-deny: no authorized plan is configured for this verifier (supply the plan and its authorization, or set InsecureSkipPlanRootCheck)` instead of reporting `not-enforced`. `Authorize` accepts no opt-out (the check was already required to pass); supply the plan and its authorization, or use `Plan: PlanSingleStep`.

- **New (K5, C-308):** workflow admission inside `Authorize`. `AuthorizeInput.Workflow` (`WorkflowOption{Principal, RsSigner, Required}`) and per call `AuthorizeInput.WorkflowStep` (`WorkflowCall{Commitment, Receipts, Step, Units, GoalDigest}`): the step is decided by `AdmitStep` (request = the operation's verb/resource/params, the PCActn's `plan.root`, the call's `now`) after context/plan resolution and BEFORE the replay claim, so a refusal never consumes the counter. A refusal is 403 with the single failing check `workflow` and reason `workflow: <code> (step <id>)` (decision `escalate` for an escalating admission); a call without a step is refused when `Required`. Off when `Workflow` is nil. Replays `authorize-workflow-fixtures.json`.
- **New (K5, C-308):** `AuthorizeOptions.Workflow` / `AuthorizeOptions.WorkflowStep` on `RequirePCA` (authorize mode). The step comes from the `WorkflowStep(r, pcactn)` callback, else the JSON body member `workflow` {commitment, receipts, step, units, goal_digest}, else none; a present but malformed member is a step `AdmitStep` denies. Same 403 / reason as `Authorize`.
- **Changed (K5):** a workflow-`Required` call with no step is refused (403, `workflow`) before the PCActn is read. An undecodable PCActn passed to `Authorize` is now 401 with check `pcactn` and reason `undecodable PCActn: ...` (was check `wire`, `wire: PCActn could not be decoded`); the workflow gate never judges it.
- **New (K5, C-315..C-319):** tokenisation vault and aggregate reads (`readvault.go`): `NewMemoryVault`, `RedactReadWithVault`, `Detokenize`; `AggregateRead` over an explicit `AggregateState` (k-anonymity floor, per-value clamp, query cap, integer micro-epsilon budget, repeated query answered free from the state) with integer-exact discrete-Laplace noise (CKS Alg. 2) from a SHA-256 block stream; `Noise: "seeded"` is deterministic from salt and query, `"secure"` (the production setting) draws a fresh CSPRNG seed. Verification only (no grant signing). Replays `vault-aggregate-vectors.json`.

- **New (K5, workflow and read-side authorization):** `AdmitStep` / `BindPromises` / `PlanRootAuthorized` (a signed DAG of steps with dataflow edges, labels, freshness and cost budgets; each step admitted only as part of the committed workflow, inputs proven from signed step receipts) and `RedactRead` / `CheckSink` / `ReadChainLabels` (signed read grants: per-class masks, tighten-only, enumeration caps, per-sink label rules, salted read receipts). Total and pure; integers only; unknown members deny. Replays `workflow-vectors.json` and `readside-vectors.json` field for field.
- **New (K7, what you see is what you sign):** the canonical approval render (`render`, `H(R)`, the approval challenge, the six-word match code), PSD2 Article 5 linking and the batch commitment, and `render_digest` on escalation requests and answers (the binding refuses an answer for another render, with none, or carrying a render the verifier did not recompute). Replays the shared `approval_*` vectors and the `approval-profiles` vectors byte for byte.
- **Breaking (migration):** with `RevocationStaleness` on, `Authorize` now also requires a non-membership proof for every capability id (default: the ids of the PCActn `cap_chain`) against the revocation root; a missing `RevocationProof` or a missing proof denies in the `freshness` check. Before, the check ran only when `RevocationProof` was set. To keep freshness-only behaviour, set `RevocationIds` to return an empty list; otherwise supply `RevocationProof`. The `RequirePCA` options carry the same fields.

- 0.5 (additive): store conformance helper. `RunStateStoreConformance` takes a factory for your `StateStore` (one new handle onto the same backend per call) and checks claim-burst, claim-concurrent (N copies of one counter across several handles admit exactly one; racing distinct counters admit the highest and never one twice), claim-durability, crash-after-claim and retry-after-timeout (the claim commits but the answer is lost: the retry is refused); `RunOperationStoreConformance` does the same for an `OperationStore` (create-once, transition-once, wrong-state, get-missing, shared, durability). A check the store declares it cannot meet is skipped, never passed; the report prints one line per check. The memory, SQL and key/value stores of this package pass it, and test doubles that are non-atomic or forget state are caught.

- 0.5 (additive): step-up client for the principal's device. `PrincipalDeviceKey` (an Ed25519 key over a `SecretStore`; `Generate`, `ImportSecret`, `ExportSecret`, `PublicKey`, `Sign`, `Delete`; `MemorySecretStore` for tests) and `StepUpClient` (`Pending` lists the unexpired step-ups, `Approve` signs the step-up's threshold message and submits the cosign, `Deny` denies through the dashboard API). Errors are `*StepUpError` with a `Kind` (`StepUpPrincipalMismatch` for the server's 403 guidance, `StepUpAPI`, `StepUpTransport`, ...); ids that could rewrite a request path are refused before any request.

- 0.5 (additive): assurance labels (T8, B7). Every `AuthorizeResult` now carries `Assurance`, a per-check report of what each passing check rests on (signature suites and level `ed25519` / `hybrid` / `pq` / `unbound_pq`, attestation level and vendor, zk system and ceremony, threshold scheme and `t`, degraded compatibility modes); the capability chain check is reported as `cap_chain`. Labels come from the verifier's configuration, never from presented evidence: a hook implements `AssuranceLabeler` or is wrapped with `WithAssuranceLabel`; `VendorVerifier` labels itself `hardware` with its vendor; an unlabelled hook is `unknown` and satisfies nothing. `AuthorizeInput.RequireAssurance` (an `AssuranceRequirement`: attestation, zk, signature `pq`, threshold schemes, `AllowPreview`) adds the `assurance` check: unmet, missing, failed, unlabelled, preview, degraded and unsupported evidence is refused before any replay state is written. A PCActn that carries `bond_ref` reports `bond` as `unsupported` (this verifier does not verify bonds), and a pass under `model_polarity: legacy` is reported degraded. Also `BuildAssuranceReport`, `UnmetAssurance`, `SignatureLevel` and `MultiRootLevel`. Replays `assurance-vectors.json` (levels, reports, requirement reasons, multi-root levels) exactly.

- 0.5 (additive): operation records (T3) and the plan lifecycle (T10). `ExecuteAuthorized` runs an authorized operation at most once against an `OperationStore` (`NewMemoryOperationStore`; `NewKVOperationStore` over any `AtomicKV`, `NewSQLAtomicKV` for a database): a `pending` record is created atomically first, an irreversible operation (the stricter of the server's and the signed class; unknown counts as irreversible) needs a `Recheck` and its expiry is always checked, then `executing`, then `committed` / `failed`; a retry is answered from the record, a stale `pending` becomes `aborted` and a stale `executing` becomes `uncertain` (never re-run; `ResolveOperation` settles it). `RecoverOperations` / `RecoverOperation`, and `NewExecutor(...).Run` (authorize + execute; a replay-only denial is answered from the record). `NewPlanRegistry` with `Draft` / `Validate` / `Commit` / `Authorize` / `Revoke` / `Get` / `Status` / `Check` / `IsPlanAuthorized` / `Context`: the plan root equals the reference's Merkle root; `AuthorizeInput.Plans` (and `AuthorizeOptions.Plans`) feeds the plan into `Authorize` and adds the `plan_state` check. Replays `operation-vectors.json` and `plan-vectors.json` scenario by scenario; concurrency tests (N parallel executions run `fn` once, N parallel claims of one plan transition have one winner), also over a SQL database.

- 0.5 (additive): per-capability revocation non-membership (T9). `VerifyNonMembership` (sorted Merkle set, UTF-8 byte order, root bound to the set size), `RevocationGateInput.Ids`/`Proof`, `AuthorizeInput.RevocationProof`/`RevocationIds` (also on `AuthorizeOptions`): after the freshness step every `cap_chain` id needs a valid proof, a missing one denies. Off unless `RevocationProof` is set. Replays the `membership` and `gate_ids` tables.
- 0.5 (additive): revocation staleness (T9). `RevocationStalenessPolicy` (`MaxRevocationAgeMs`, per-class `Staleness` windows, `AllowUnsignedRootForIrreversible`) caps how old the revocation state may be by the action's effective class (`EffectiveReversibility`: the stricter of the server's class and the signed one; missing or unknown counts as irreversible; irreversible default 2 min). `CheckRevocationAge`, `RevocationMaxAgeMs`, `CheckRevocationEpoch` (guardian-signed epoch under the same pin rules as the ledger verifiers: Ed25519, ML-DSA and hybrids; an unregistered suite is refused), `SignRevocationEpoch`, and `RevocationGate`. `AuthorizeInput.RevocationStaleness` / `RevocationState` / `GuardianPublic` / `GuardianPins` (also on `AuthorizeOptions` for `RequirePCA`) add the required `freshness` check; `IsRevoked` keeps working unchanged and the whole feature is off unless the policy is set. A missing state source or an invalid policy denies with the missing component named. Replays `staleness-vectors.json` (epoch and gate rows exactly, including reasons).

## 0.4.1

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. In Go: `PolicyCaveats(grant, chain any) any` and `EvaluateCaveats(caveats any, ctx map[string]any) (ok bool, failed []string)` (caveats.go), total and fail-closed; `ctx` uses the conformance field names (`now`, `delegation_depth`, `blast_radius`, `reversibility_class`, `recent_action_times`, `action.params`). Implemented: `max_spend`, `expires`, `not_before`, `rate`, `max_blast_radius`, `reversibility_max`, `delegation_depth`, `budget_alloc`; every other type (note, a second envelope, predicates, tool_schema, unknown) is unsatisfied. `VerifyPCActnCore*` and the `RequirePCA` middleware are unchanged: they do not evaluate caveats; a resource server enforcing a grant's caveats calls `EvaluateCaveats(PolicyCaveats(grant, chain), ctx)` with its own action params. Runs the new `primitives.caveat_eval` corpus section.
- Wire: threshold share signatures are validated PER SUITE (they were a fixed 64 bytes, so a pure ML-DSA-65 share could never be carried). `alg` absent == ed25519 (64-byte `sig`, no `pq_sig`); `ml-dsa-65`: 3309-byte `sig`, no `pq_sig`; `hybrid-ed25519-ml-dsa-65`: 64-byte `sig` + 3309-byte `pq_sig`; a non-string `alg` (incl. null) or an unknown suite fails wire. A share's `pq_pk` is not judged by wire (the threshold check judges it). The wire reason is now `threshold.shares[i]: 'sig' is not canonical base64url (N bytes) for alg '<alg>'`. The conformance runner skips `requires:"<alg>"` vectors for suites Go does not implement (ml-dsa-87, slh-dsa-sha2-128f).
- BREAKING (security): the `PCA-Action` header is STRICT unpadded base64url of UTF-8 text. New exported `DecodePCAHeader(value string) (string, error)` (`ErrPCAHeader`): non-empty, alphabet `A-Z a-z 0-9 - _` only, no `=`, no whitespace (nothing trimmed), length mod 4 != 1, zero trailing bits, then strict UTF-8 (a leading BOM is kept). The middleware's lenient decoder (padded fallback) is removed; any failure takes the existing 401 "PCA-Action header is not valid base64url" path. Runs the new `primitives.pca_header` corpus section.
- Version: Go module versions are git tags (no version string in the sources); release this as `v0.4.1`.

- R4-01: `VerifyChainPolicy` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Signature: `VerifyChainPolicy(chain []any, expectedRootIssuer string, haveIssuer bool, allowed []string, pqPins map[string]string, trustedRoot map[string]any) (string, bool)`. A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `trustedRoot` is the root itself (same content hash, i.e. the verifier's stored grant), or `pqPins[root.issuer]` equals the root's `pq_pk` (a differing pin is a refusal).
